# artifact-brainstorming 設計書

- 日付: 2026-10-12
- 設計図（決定の見える化）: https://claude.ai/artifact/HsrjHFnpfbfXdHJkNfVfRx
- 元にした観察: 別セッションで、アーティファクト上の質問カードを使って brainstorming を進めた流れ（2026-10-09）

## 目的

brainstorming の問いを、前後の文脈（図や本文）と一緒に、アーティファクト上で見て答えられるようにする。チャットに選択肢だけが出ると、文脈が分からず判断しにくいため。

- 成功の条件:
  - どの問いも、判断に要る文脈と同じ場所で読み、同じ場所で答えられる。
  - 何をどこまで決めたかが、図解の上で一目で分かる。
- 範囲:
  - repo やドメインに依存しない汎用の skill にする。
  - brainstorming の手順そのものは変えない。

## 決定事項

| ID | 決定 |
|---|---|
| B1 | brainstorming の上に重ねる層にする。分類 → 質問 → 案 → 設計 → 設計書 → 計画、の段階は brainstorming に従う。この skill が定めるのは、質問・承認・設計の提示をアーティファクトで行う場と受け渡しだけ。 |
| B2 | 壁打ちの前に、対象を理解するための図解を必ずアーティファクトに作る。規模に応じて薄くする。 |
| B3 | 図解を公開したら、ユーザーが疑問を解消する時間を取る。「進めて」の合図で Q0（目的・前提）を出す。理解の質疑と壁打ちの回答は混ぜない。 |
| B4 | 図解の図は、ノードと矢印を配列で書いて draw.io 風の SVG を描く部品で描く。ノードに問いの id を付けて目印を置く。Mermaid は使わない。 |
| B5 | 特定の箇所に結び付かない問い（全体の問い）も、文脈の意図が最も近いところに目印を置く。専用の置き場所は作らない。 |
| B6 | 回答を受けて更新したら、チャットには 1〜2 行（決定と、次の問いへのリンク）だけ書く。 |
| B7 | 「文脈が足りない」質問には、問いの近くの本文に補足（図・具体例の表・段落）を足して答える。スレッドには足した場所を 1 行で伝え、問いは開いたまま回答を待つ。 |
| B8 | 自動返信（auto-react）の内容が実際の対応と同じなら、スレッドに何も書かない。食い違ったとき（約束・見通し・余計な質問）だけ訂正を 1 行書く。B7 の 1 行も、自動返信がその場所をすでに伝えていれば省く。 |
| B9 | 決めた問いを取り消すときは、元の問いに取り消しの印と「→ 作り直した問い（理由）」を付けて残す。作り直した問いは同じ目印の位置に出し、後続の問いは「要確認」にする。 |
| B10 | 設計は図解に「設計」の章を足し、節ごとに出して承認を取る。各節から根拠へ文中リンクを張る。 |
| B11 | 外部レビュー（Codex・Opus）は skill に入れない。ユーザーがその都度指示する。 |
| B12 | 設計書の後に「アーティファクトで続ける」を選んだときは、設計書の確認と承認までをアーティファクトで行う。実装計画はチャットで writing-plans を使う。 |
| B13 | 引き継ぎ手順を持つ。アーティファクトの URL と図解の中のデータを正とし、引き継ぎ書には方針と途中の議論だけを書く。古いセッションの見張りを止めてから、新しいセッションで見張りを始める。 |
| B14 | ページから送れないときは、理由と、送るはずだった文面のコピー欄を出す。 |
| B15 | 問いの意図に近い文脈が図解に無いときは、関係する章に段落・図・表を足してから（無ければ章を新設して）目印を置く。 |
| B16 | 名前で呼んだときだけ起動する。名前で呼ぶとは、`/artifact-brainstorming` と打つか、「アーティファクトで壁打ちして」と明示することを指す。 |
| B17 | `~/.claude/skills/` に個人用として置く。 |
| ― | 質問は 1 問ずつ出す（ユーザーの CLAUDE.md による）。 |

### ユーザーの memo（必ず反映する）

1. リンクは文末にまとめず、文中の該当する言葉に張る。
2. 回答した問いはすぐ折りたためる。
3. 問いはセクションに並べず、図や文言の中の目印から開くポップオーバーで出す。
4. 設計書を作ったら、チャットに戻るか議論を続けるかを選べる。
5. チャットで問うときは、質問文と選択肢だけで判断できるように、背景と具体例を入れる。

### 観察から取り込む要望

- ケースは最初から具体例の表で示す。抽象的な説明は 2 回差し戻された。
- 選択肢には、どこが変わって何が起きるかを書く。図で示せるなら図にする。

## §1 構成

- 名前: `artifact-brainstorming`
- 置き場所: `~/.claude/skills/artifact-brainstorming/`
- 説明文: 名前で呼ばれたとき、またはアーティファクト上で壁打ちしたいと明示されたときに使う。自動では発火させない。

| ファイル | 中身 |
|---|---|
| `SKILL.md` | 起動の条件、brainstorming との重ね方、全体の流れ、各段で守ること。手順は短くし、詳細は参照ファイルへ回す |
| `references/loop.md` | 回答を受けてから再公開するまでの手順、自動返信との付き合い方、送れないとき、版の衝突、引き継ぎ |
| `references/questions.md` | 問いの書き方（状況 → 具体例の表 → 選択肢と影響 → 推奨と理由）、置き場所の決め方、取り消し方 |
| `templates/page.html` | 図解ページのひな形。図の描画部品、目印とポップオーバー、折りたたみ、送信とコピー欄 |

brainstorming の手順そのもの（分類・案の比較・設計書・writing-plans への受け渡し）は書き写さず、参照するだけにする。

## §2 流れ

1. **起動**: `/artifact-brainstorming` で呼ばれたら brainstorming を起動し、分類を宣言する。
2. **図解を作る**: 対象の流れと前提を章と図でまとめる。`comments` の機能を付けて公開し、見張りを始める。チャットには 1〜2 行とリンクを書く。
3. **理解の質疑**: 答えは本文に足す。「進めて」の合図を待つ。
4. **Q0**: 目的・成功基準・仮定を、図解の「目的」の文言の近くに出す。
5. **分岐を 1 問ずつ**: 親の分岐から順に、文脈の中の目印に出す。回答のたびに §3 のループを回す。brainstorming の案の比較（2〜3 案）も、比較表付きの問いの 1 つとして出す。
6. **設計**: 「設計」の章を足し、節ごとに承認を取る。
7. **設計書**: brainstorming の既定の場所に書く。ユーザーの指定があればそちらに書く。
8. **分かれ道**: 「チャットに戻る」か「アーティファクトで続ける」かを聞く。続けるなら、設計書の要点を図解に載せ、確認と承認までをアーティファクトで行う。
9. **実装計画へ**: チャットで writing-plans を起動し、この時点で見張りを止める。

コンテキストが溜まったら、どの段でも §3 の引き継ぎ手順を使う。

## §3 受け取りループと、うまくいかないとき

### ループ（ページから送られるたびに）

1. 通知を受けたら、そのスレッドだけでなく全スレッドを読む。
2. 届いたものを 3 種類に分ける: 問いへの回答 ／「文脈が足りない」質問 ／ 普通のコメント。
3. 種類ごとに対応する。
   - 回答: 問いを「決定」にして決定文を書き、折りたたむ。図の決定表示を更新し、次の問いを 1 つだけ出す。
   - 質問: 問いの近くの本文に補足を足す。問いは開いたまま。
   - 普通のコメント: 指摘どおり本文を直す。
4. 自動返信と実際の対応を見比べる。食い違っていれば訂正を 1 行書く。自動返信が約束したことは、実行するか訂正する。
5. ページのスクリプトの構文を確かめてから、同じファイルで再公開する。版のラベルは「Q3 決定・Q4 追加」の形にする。
6. 済んだスレッドを解決にする。やりとりが続いているものは開いたままにする。
7. チャットに 1〜2 行とリンクを書く。

### うまくいかないとき

| 場面 | どうするか |
|---|---|
| ページから送れない | ページが理由とコピー用の文面を出す。チャットに貼られたら、ページから届いたときと同じループで処理する |
| 決めた問いの前提が崩れた | B9 の手順で取り消し、作り直す |
| 他で公開された新しい版があった | 上書きしない。別のセッションが処理していれば、自分の見張りを止める。していなければ、新しい版に自分の変更を重ねて公開する |
| コンテキストが溜まった | 引き継ぎ書（方針と途中の議論だけ）を書く → 自分の見張りを止める → 新しいセッションを起動してもらう（起動方法はユーザーの環境に任せる）→ 新しいセッションで見張りを始め、全スレッドを読んで未処理を確かめる |

## §4 ページの部品（templates/page.html）

| 部品 | 仕組み |
|---|---|
| 図 | 図ごとに「ノード（形・列・行・ラベル）と矢印」の配列を書くと、方眼の上に draw.io 風の SVG が描かれる。ノードに問いの id を書くと、そのノードの角に目印が付く |
| 文言の目印 | 本文の言葉を `<span data-q="Q3">` で囲むと、その直後に目印が付く |
| 目印の見た目 | 小さな番号札で、状態ごとに見た目を変える: 回答待ち＝強調色、決定＝チェック、取り消し＝取り消し線、要確認＝注意色 |
| ポップオーバー | 目印を押すとその場に開く（スマホでは画面下から出る）。中身は「状況 → 具体例の表 → 選択肢と影響 → 推奨と理由」、補足欄、「回答を送る」「文脈が足りない：質問する」 |
| 折りたたみ | 送れたら、その場で閉じて目印を「送信済み」にする。決定後に目印を押すと決定文だけが出て、詳細は開閉できる |
| 文中リンク | 根拠への参照は、本文の言葉そのものを図や章へのリンクにする |
| 問いのデータ | 1 つの配列で持つ。項目は id・目印の場所・状態（回答待ち／決定／取り消し／要確認）・本文・選択肢・推奨・決定文・取り消しの理由。設計の節の承認も同じ形（OK／修正あり）にする |
| 送信 | 目印の場所を指すコメントとして Claude に送る。文面は `[タグ] Q3「題」への回答 / 選択：a / 補足：…`。送れないときは理由とコピー欄を出す |
| 上部の進み具合 | 「決定 5 ／ 回答待ち 1」の 1 行と、回答待ちの目印へ飛ぶリンクだけを置く。問いを並べる欄にはしない |

## §5 試し方

1. **ひな形のページ**
   - 入れるもの: サンプルの問い（回答待ち・決定・取り消し・要確認を 1 つずつ）。
   - 確かめること: 図、目印、ポップオーバー、折りたたみ、送れないときのコピー欄、スマホ幅、ダーク表示。
2. **通しの試運転**
   - 新しいセッションで、小さな題に `/artifact-brainstorming` を使う。
   - ユーザーがページから 2〜3 問答え、設計 1 節・設計書・分かれ道まで進める。
   - チャットに書く量が 1〜2 行に収まるかも確かめる。
3. **うまくいかない場面**
   - 試運転の途中で、1 問を取り消す。
   - 見張りを止めた状態で送る。
   - 引き継ぎを 1 回行う。

skill の書き方（説明文、手順の短さ）は、実装のときに writing-skills の手順で整える。
