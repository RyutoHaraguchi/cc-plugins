# 受け取りループと、うまくいかないとき

## ループ（ページから送られるたびに）

1. 通知は毎回、`ArtifactComments` の `read` を `thread_id` なしで呼んで処理する。結果に「他のスレッドにも自分宛てのコメントがある」とあれば、publish の前にすべて処理する。通知は 1 件ずつ来るが、他にも未処理が残っている。
2. 届いたものを 3 種類に分ける。
   - 問いへの回答: 本文が `[タグ] ID「題」への回答` で始まる。
   - 「文脈が足りない」質問: `[タグ] ID「題」について質問` で始まる。
   - 普通のコメント: それ以外（図の文言の指摘など）。
3. 種類ごとに直す。
   - 回答: その問いを `done` にして `answer` を書く。図の決定表示（ノードのラベルなど）を直す。次の問いを 1 つだけ `open` で足す。
   - 質問: 問いの近くの本文に補足（段落・図・具体例の表）を足す。問いは `open` のまま。
   - 普通のコメント: 指摘どおり本文を直す。
4. スレッドの自動返信を読み、実際の対応と見比べる。
   - 食い違っていたら（約束・見通し・余計な質問）、訂正を 1 行 `reply` する。
   - 同じなら何も書かない。質問への補足でも、自動返信が足した場所を伝えていれば書かない。
   - 自動返信が約束したことは、実行するか訂正する。
5. ページの 3 つのスクリプト（core / data / ui）の構文を確かめてから、同じファイルパスで publish する。`PAGE.html` は publish するページのファイル、`$SCRATCH` はスクラッチパッドのディレクトリ。`NG:` が出たら直す。
   ```
   for id in core data ui; do perl -0ne "print \$1 if /<script id=\"$id\">(.*?)<\/script>/s" PAGE.html > "$SCRATCH/ab-$id.js" && [ -s "$SCRATCH/ab-$id.js" ] && node --check "$SCRATCH/ab-$id.js" || echo "NG: $id"; done
   ```
   `label` は「Q3 決定・Q4 追加」の形にする。
6. 済んだスレッドを `resolve` する。やりとりが続いているものは開いたままにする。
7. チャットには最大 2 行だけ書く: 決定を 1 文、次の問いへのリンク（例「Q3 を a で決定。次は Q4」）。箇条書き・問いの再説明・publish 前の「公開します」は書かない。ユーザーがチャットで直接聞いたことへの答えはこの限りでない。

## うまくいかないとき

| 場面 | どうするか |
|---|---|
| ページから送れない | ページが理由とコピー用の文面を出す。ユーザーがチャットに貼ったら、ページから届いたときと同じループで処理する |
| 決めた問いの前提が崩れた（外部レビューやユーザーの深掘りで） | `questions.md` の「取り消して作り直すとき」の手順 |
| publish したら、他で公開された新しい版があった | 上書きしない。別のセッションが処理していないか確かめる。していれば自分の見張りを止める（`ArtifactComments` の watch を off）。していなければ、新しい版を読み直して自分の変更を重ねて publish する |
| コンテキストが溜まった | 下の引き継ぎ手順 |

## チャットで決まったとき

ユーザーがチャットで問いを決めたら（例「それなら a でいいです」）、ページからの回答と全く同じに扱う。その問いを `done` にして、`answer` に「（チャットで決定）」を付けて書く。次の問いを足し、同じ構文チェックをして publish する。ページから送り直すよう頼まない。

## チャットで文脈を聞かれたとき

ページの「文脈が足りない」ボタンの代わりにチャットで文脈を聞かれたら、「文脈が足りない」（ループの手順 3 の「質問」と同じ扱い）として、チャットで答え、同じ補足を問いの近くの本文にも足す。

## 引き継ぎ

1. アーティファクトの URL と、ページの data（決定・未決の問い）を正とする。引き継ぎ書には次だけを書く。
   - 方針
   - 途中の議論
   - ページに載っていない約束
   - 元のセッションの transcript の場所
2. 自分の見張りを止める（`ArtifactComments` の watch を off）。
3. ユーザーに新しいセッションを起動してもらう。起動方法はユーザーの環境に任せる（orca など）。同じアーティファクトでフォークや別セッションを開いたときも、続ける側が古い側の見張りが止まっているか確かめる（または止めるようユーザーに伝える）。両方に通知が届くため。
4. 新しいセッションでは、アーティファクトを `read` してから watch を始める。全スレッドを読んで未処理を確かめる。

## 終わるとき

writing-plans に移る時点で、見張りを止める。以降にページから送られても受け取らない。
