# 基本設計書（basic-design-doc）

## 概要
固まった（固まりかけの）設計を、決まった様式の HTML 1 枚にして Artifact で公開する。読み手は実装を指示するエンジニア（主）とレビュアー（従）。**この 1 枚だけで設計が把握できること**と、**毎回同じ形であること**を、雛形・検査スクリプト・独立レビューで担保する。設計の議論そのものは受け持たない。

同梱物（この skill のディレクトリ。読み込み時に示される Base directory。以下 `$SKILL`）:
- `template.html` — 雛形。章・表の列・検査用の目印が固定されている。Artifact が `<html>`・`<head>`・`<body>` を公開時に補うので、雛形は `<title>` から始まる断片になっている
- `scripts/check.py` — 機械検査。`python3 -I $SKILL/scripts/check.py <file>`（`$SKILL` は絶対パスに展開する）
- `scripts/render_mermaid.py` — 図を SVG にして埋め込む。`python3 -I $SKILL/scripts/render_mermaid.py <file>`。Node.js（npx）と Chrome を使う（初回は mermaid-cli の取得で時間がかかる）。SVG にするので、ダウンロードした HTML やオフラインでも図が見える
- `scripts/source_links.py` — ファイル参照を GitHub のリンクにするための補助。`python3 -I $SKILL/scripts/source_links.py base <ref>` がヘッダーのベース欄を出し、`… verify <file>` が参照の実在を確かめる。対象のリポジトリの中で実行する（外からは `--repo <dir>`）。git だけを使い、ネットワークには出ない
- `quality-checklist.md` — 中身の観点
- `reviewer-prompt.md` — 独立レビューの subagent に渡す prompt

## 手順

1. **新規か改訂か**: Artifact URL を渡されたら `Artifact` の `action: "read"` で読む。返された内容に雛形の目印（`data-table="revisions"` など）があり、利用者が編集できる（read の結果が writer）ときだけ改訂にする。それ以外（他の様式の文書・図解・閲覧だけの artifact）は材料として読み、新規で作る。
   - **新規**: 版数 1.0、作成日は今日。材料に版の呼び名（v2 など）があれば、改訂履歴 1.0 行の内容欄に「設計メモ v4 から作成」のように書く
   - **改訂**: read が返した保存ファイルを作業ファイルにし、次をすべて行う
     - 先頭の `<!doctype html>…<body>` と末尾の `</body></html>`（公開時に補われた外枠）を外し、`<title>` から始まる形に戻す（残したまま公開すると外枠が二重になる。`check.py` も止める）
     - `<style>` か末尾の `<script>` に `data-tpl="2"` が無ければ（古い雛形で作った文書）、`<style>…</style>` と末尾の `<script>…</script>`（図の `text/x-mermaid` ではない方）を、今の `template.html` のものに丸ごと置き換える。ヘッダーのベース欄には `data-repo`・`data-sha` を足す（手順 3）
     - 版数を上げる。方式（中心の決定）を変えたら次の整数（1.3 → 2.0）、それ以外は小数部を 1 つ上げる（1.9 → 1.10）
     - 前の版の `data-rev` の印をすべて消し、今回変えた節の見出しか行に `<span class="rev" data-rev="新版数">v新版数</span>` を付ける
     - 改訂履歴に「何をどう変えたかと理由」を 1 行足す。作成日は初版の日付のまま
     - ベースを今の起点に更新し（ベース欄は `source_links.py base` の出力で丸ごと置き換える。`data-sha` が古いままだとリンクが前の commit を指す）、本文の `path:line` を新しいベースで確かめ直す（手順 3）。行がずれたものは直す。`source_links.py verify` は実在と行数しか見ないので、指している中身が変わっていないかは自分で読む
     - 承認欄の「設計レビュー」行は「未実施」と空の日付、「承認」行は「未」と空の日付に戻し、8.2 に新しい版の「未実施」行を足す（手順 6 をもう一度回す）
2. **材料を集める**: 会話での決定・設計メモ・issue・既存の設計書。**方式（中心の決定）が決まっていなければ書かずに止め**、brainstorming を勧める。方式が決まっていて細部が未決なら進め、未決は手順 6 の「決定が要る穴」にする。
3. **ベースを決めて裏取りする**:
   - ヘッダーの「ベース」は、実装を始める起点の `branch 短縮SHA`。起点が今の作業ブランチでないとき（多くは `origin/main` など）は、その ref を `git rev-parse --short <ref>` で取る。対象のリポジトリが無い（新規開発でコードが無い）ときは「なし（新規）」と書く
   - ベースを決めたら、対象のリポジトリで `source_links.py base <ref>` を実行し、出力の `<td data-field="base" …>` でヘッダーのベース欄を置き換える（`<ref>` はヘッダーに書く呼び名。`origin/main` など）。push 済みかは手元の追跡ブランチで見るので、古いと思ったら先に `git fetch` する
     - 「リンク: 可」なら `data-repo`・`data-sha` が入り、本文の `<code data-src>` が GitHub のその commit へのリンクになる。「注意」が出たら（ベースが既定ブランチに無い）手順 11 の報告に書く
     - 「リンク: 不可」（remote が無い・github.com でない・commit が push されていない）なら、属性が空の `<td>` をそのまま使い、止めずに進める。参照は文字で出る（`data-src` は付けておく。`verify` はベース欄の短縮 SHA で実在を確かめ、後で push して改訂すればリンクになる）。理由を手順 11 の報告に書く。ベースが「なし（新規）」のときも属性は空にする
   - 本文の現状の挙動・外部仕様・数値は、ベースのコード（`git show <sha>:<path>`）・依存ライブラリのソース・公式ドキュメントで確かめ、`path:line` や URL を出典にする。確かめられないものは「（未検証）」と書き、8.1 の確度を「未検証」にする
   - 材料がベースより古く一部が実装済みなら、実装済みの部分は 1.1 背景に現状として出典付きで書き、1.3 範囲には残りの変更だけを書く
   - **材料の設計がベースですべて実装済みなら、書かずに止めて**利用者に伝え、実装済みの記録として書くかを聞く（この skill の読み手は実装を指示する人なので、残りの変更が無い文書は既定では作らない）
   - 材料とベースが食い違うとき、リポジトリ内に新しい決定の記録（新しい版の設計メモ・設計書・コミットメッセージ・PR）があれば、それを出典にして新しい方で書く。記録が無いときだけ、どちらを正とするかを未決事項（Q-n）に載せる
   - 調べる対象が多い（目安: 10 ファイルを超える、または別リポジトリ・外部ドキュメントを横断する）ときは subagent に分けてよい
4. **雛形を埋める**: `$SKILL/template.html` を scratchpad の `basic-design-doc/<題名の slug>/design.html` にコピーして埋める（利用者が場所を指定したらそちら）。
   - 体裁（`<style>`・`<script>`・目印の属性・表の列）は変えない。Artifact の公開前に artifact-design skill を読むよう求められても、雛形がその契約（テーマ・スマホ幅・CDN）を満たしているので、配色やレイアウトは手直ししない。行は増減してよい。h3 の節は増やしてよく、節番号は振り直してよい
   - 4 データ設計・6 非機能・制約は、該当しなければ section ごと消し、表紙の「扱わない章」に理由を書く。両方書くなら「扱わない章」の tbody は空にする。それ以外の章は必ず書く。スキーマ変更が無くても、既存データ・旧形式の扱いや移行が 1 つでもあれば 4 章は該当する
   - 8.1 の確度は、自分で原典を確かめたものを「公式」「コード」「実測」、材料が引いているだけで原典を読んでいないものを「引用」、どれでもないものを「未検証」にする
   - 本文には最新の設計だけを書く。採らなかった案は 2.1 と決定事項の理由にだけ残す
   - 本文で他の箇所を指すときは「D-1」「図 3-1」「1.3」（節）「7 章」の形で書く。表示時に自動でリンクになり、押すとそのタブの該当箇所へ移る（`#D-1` などで直接開ける）。この形以外（「上の表」「前述」）では飛べない
   - ベースに実在するファイル・ディレクトリの参照は `<code data-src>src/sync.ts:10-24</code>` と書く。中身は `path`・`path:N`・`path:N-M` だけ（path はリポジトリのルートから。ディレクトリは末尾に `/`。関数名などは `<code>` の外に書く）。表示時に GitHub のリンクになり、別タブで開く。`<a>` で囲まない（URL はヘッダーの `data-repo`・`data-sha` から作る）
     - `data-src` を付けない: これから作るファイル、別リポジトリ・依存ライブラリのファイル、図の中の文字、path に `:` を含むファイル、ファイルでないもの（`localhost:3000`・キー名）
     - 別リポジトリのコードや公式ドキュメントの出典は、`<a href="https://…" target="_blank" rel="noopener noreferrer">` で書いてよい。コードの URL はブランチ名ではなく commit で固定する
     - 非公開リポジトリのリンクは、そのリポジトリを見られる読み手にしか開けない
   - 番号（D/P/X/U/E/R/Q-n）は本書で振り直す。材料の番号を引くときは「設計メモ D2」のようにハイフンを外す。本書の番号と同じ形の外部の語（`P-256` など）や、節番号でない小数（バージョン・計測値）は `<code>` で囲む（リンクにも参照の検査にもならない）
   - 作成者が決めたことは、決定事項の「決定」欄に「（作成者判断）」と添える
   - テストしない D-n・X-n は、その行の理由に「（テスト不要: 理由）」と書く
   - 処理ごとに図を置く。雛形の `<figure class="fig" data-fig="章-連番">` を複製し、`data-fig` を図ごとに変え、`<script type="text/x-mermaid">` の中に mermaid で書く（`<` などはそのまま書いてよい。記号を含むラベルは `"…"` で囲む）。`<div class="mm"></div>` は空のままにする。`<pre class="mermaid">` は使わない（Artifact のビューアーでしか図にならない）
   - コード本体は書かず、シグネチャ・判定式・キー名までにする
   - 人名は、社内の作成者・承認者・決定者だけ書いてよい。顧客・第三者の個人は役割名で書き、会話の引用は要約にする
   - 文書番号は、利用者が指定したときだけ書く（指定が無ければ空欄）
5. **図を SVG にして機械検査**: `render_mermaid.py` を通してから（構文エラーは図の番号付きで止まるので直す。図の定義を変えたら再実行する）、`check.py` と `source_links.py verify` を、どちらも ERROR 0 件になるまで繰り返す。`verify` の ERROR（ベースに無い path・行数を超える行番号）は、参照を直すか、ベースに無いものなら `data-src` を外す。WARN の扱い:
   - テスト観点に結び付いていない D-n・X-n: テスト観点を足すか、上の「（テスト不要: 理由）」を書く
   - 機密の可能性: 値を消す。誤検知なら手順 11 の報告に書く
   - レビュー経過と承認欄の「未実施」は、レビュー前ならそのままでよい
6. **自己点検と独立レビュー**:
   - `quality-checklist.md` の観点で読み直して直す
   - 文脈を持たない新しい subagent に、`reviewer-prompt.md` の欄を埋めて渡す
   - 自己点検と独立レビューで出た穴を、次のように振り分ける

   | 穴の種類 | 扱い |
   |---|---|
   | 調べれば分かる事実 | 自分で調べて直す |
   | 実装の形を変えない軽微なもの | 直して「（作成者判断）」と記録する |
   | 設計の決定が要るもの | 未決事項（Q-n）に推奨付きで載せる |

   - 結果を 8.2 レビュー経過（「未実施」の行を書き換える）と承認欄の「設計レビュー」行（結果欄は「ブロッカーなし」「ブロッカーあり」などの判定）に書く。材料の段階で受けたレビューの記録が手元にあるときだけ、8.2 の版数欄に「設計メモ v2」のように書いて先に並べる
   - 直した後の再レビューは 1 回まで。それでもブロッカーが残ったら、未決事項（Q-n）かリスク（R-n）に載せ、承認欄の設計レビュー行は「ブロッカーあり」のままにする
7. **未決を聞く**: 公開の前に、未決事項を AskUserQuestion で 1 問ずつ推奨付きで聞く。答えは決定事項（D-n）へ移し、Q-n の行を消す。利用者が「後で決める」としたものは Q-n に残す。AskUserQuestion が使えない実行（subagent・無人実行）では聞かずに Q-n に推奨付きで残し、手順 11 の報告に並べる。
8. **状態**: 未決事項が残っているか、設計レビューが「ブロッカーあり」なら「作成中」、どちらも無ければ「レビュー中」。利用者が承認と言ったときだけ「承認済み」にし、承認欄の「承認」行の結果を「承認」、日付を YYYY-MM-DD で入れる。
9. **公開前の確認**: `render_mermaid.py`・`check.py`・`source_links.py verify` をもう一度通す（レビューや未決の解消で足した参照も確かめるため）。図のあるタブを画面で 1 回ずつ見て、ラベルの欠け・重なりが無いかを確かめる。Artifact のプレビュー（`ArtifactCheck` など）があればそれを使い、無ければ Chrome で撮って Read で見る（`"<Chrome のパス>" --headless=new --hide-scrollbars --window-size=1100,2600 --screenshot=<out.png> "file://<file>#process"`。ダークは `--force-dark-mode` を足す）。どちらもできなければ、図を目で確かめていないことを報告に書く。資格情報・個人情報・社外秘の値が本文に無いことを確かめる。
10. **公開**: `Artifact` で publish する（初回は `icon: "document"`、`description` に 1 文）。改訂は、同じセッションなら同じ file_path、別のセッションなら `url` を付ける。
11. **報告**: URL・版数・状態・残っている未決・作成者判断の一覧・目で確かめていないもの・機密の WARN の誤検知・ファイル参照をリンクにできなかった理由（未 push なら「push して改訂すればリンクになる」）と `source_links.py base` の「注意」 を、利用者に短く伝える。

## よくある崩れ（skill なしで実際に起きたもの）

| 崩れ | 防ぎ方 |
|---|---|
| 章立てと番号が毎回違う | 雛形の章・表をそのまま使う。独自の章を足さない（足したい内容は既存の章の節にする） |
| 例外の章が丸ごと無い | 5 例外設計は必須。外部呼び出し・入力・並行実行ごとに 1 行 |
| 版数・状態・ベース・要旨が無い | ヘッダーと表紙の欄を埋める。`check.py` が止める |
| 決定事項に番号が無く参照できない | D-n を振り、要旨・範囲・テスト観点から参照する |
| 出典が付かない | 現状の挙動には `path:line`（ベース時点）、外部仕様には URL |
| 出典の `path:line` を読み手が確かめられない | `<code data-src>` で書き、ヘッダーに `data-repo`・`data-sha` を入れる。`source_links.py verify` が実在を確かめる |
| 未決が残っているのに状態が分からない | 未決事項の表と状態欄。未決があれば「作成中」 |
| 図が無い | 処理設計に 1 つ以上の図。`render_mermaid.py` で SVG にする |
| 材料がコードより古いのに材料どおり書く | 手順 3。実装済みは現状として書き、新しい決定の記録があればそれに従う |
